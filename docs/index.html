Deterministic Multi-Agent Coordination for Pi

An authoritative, local-first runtime for recursive Pi subagents. Semantic agents reason about code; an out-of-band broker enforces mechanical borrow checking, write fencing, durable mailboxes, and atomic tasks.

The Problem: Why Multi-Agent Coding Breaks Down

Most agent frameworks treat collaboration as a prompt-engineering problem. Subagents are given prompt instructions—"coordinate with your peers", "do not edit files assigned to another agent"—and left to share the same workspace or global chat channel.

Under real programming workloads, prompt-level conventions inevitably break down:

💥
Silent File Clobbering
Two agents editing the same workspace simultaneously overwrite each other's edits. Neither git nor the LLM notices the collision until code vanishes.
🏎️
Parent-Child Write Races
While a child agent refactors a module, the user or parent continues editing. Without physical write locks, the parent mutates files out from under the child.
🛑
Synchronous Call-Stack Deadlocks
When a child pauses to request user guidance, conventional tools block the parent's JavaScript event loop, freezing the entire session.
📢
Context Window Flooding
Unscoped broadcast chatrooms spam every agent with every peer's internal thoughts, rapidly exhausting context limits with conversational noise.
👻
Ghost Duplication on Retries
Transport timeouts during agent spawn or task assignment cause naive retries to create duplicate workers or parallel competing tasks.
🔓
Symlink & Alias Bypasses
File locks that check purely lexical strings are trivially bypassed when an agent writes through a directory alias, junction, or relative symlink.

The Key Insight: Separation of Concerns

Core Thesis
"Agents make semantic decisions. A deterministic broker enforces coordination correctness."
An LLM should never be trusted to act as a mutex, a distributed lock manager, an identity authority, or an atomic queue.

pi-safe-agents-team introduces an authoritative out-of-band coordinator daemon that sits between your Pi agent sessions and the underlying filesystem. It models workspace concurrency after the Rust borrow checker:

  • Hierarchical Resources: Files and folders form a strict permission and borrow hierarchy.
  • Shared vs. Mutable Borrows: Multiple agents may hold shared read leases simultaneously. Only one actor may hold an exclusive mutable lease across any overlapping path tree.
  • Time-Bounded Leases & Heartbeats: Leases automatically reclaim if an agent crashes or stalls, preventing permanent deadlocks without stack locks.
  • In-Flight Write Fencing: Active writes establish ephemeral exclusion fences so a lease expiring mid-mutation cannot hand the file to a competitor until the disk write finishes.

Broker Architecture

The architecture connects full-featured Pi SDK AgentSession instances to a single, serialized coordinator process over local IPC:

In-Flight Write Fences (begin_write & end_write)

Authorization and filesystem mutation are not atomic on standard OS filesystems. To prevent race conditions where a lease expires while a slow file write is actively executing:

  1. Worker acquires a mutable borrow (e.g. 5-second lease).
  2. Before invoking node:fs, the tool calls resource.begin_write({ path, fenceMs }).
  3. The coordinator authorizes the write and establishes an active in-memory write fence.
  4. If the 5-second lease lapses during a 10-second file write, the fence continues to deny competing leases.
  5. Once mutation completes, the worker calls resource.end_write({ fenceId }), immediately releasing queued waiters.

Root Host Guard (hostGuard: true)

The user interactively driving Pi should not be forced to manually define and lease every single file before typing an edit. The Root Host Guard transparently bridges interactive freedom with multi-agent safety:

  • Root edit and write tool calls are intercepted before touching disk.
  • Targets are checked against resource.begin_write({ path, hostGuard: true }).
  • Undeclared paths pass through freely without prior declaration.
  • Declared paths leased or fenced by active child workers are immediately vetoed with a visible explanation.
  • Fail-closed guarantee: If the broker daemon crashes or disconnects during a coordinated write, the root guard fails closed to protect in-flight worker writes from collision.

Actor-Scoped Operation Deduplication

Network blips and IPC timeouts often cause callers to wonder whether their creation succeeded. Naive retries result in duplicate subagents and parallel conflicting tasks:

  • agent.spawn and task.create accept an actor-scoped operationId.
  • The client generates an operation ID and retries ambiguous failures with the same key.
  • The coordinator journals the result. If a matching retry arrives, the coordinator returns { ...originalResponse, replayed: true } without repeating the state transition.
  • Mismatched reuse of an existing operation ID fails closed with IDEMPOTENCY_CONFLICT.

Deadlock-Free Clarification

When a child encounters ambiguity, conventional tools block the parent turn synchronously, causing call-stack deadlocks:

  • The child calls agent_send({ type: "clarification", to: "parent", body: "Which auth scheme?" }).
  • The tool signals terminate: true, immediately releasing the model turn and execution capacity.
  • The child transitions cleanly to the waiting state.
  • When the parent or user provides an answer via agent_reply, a fresh prompt turn wakes the child.

Installation

npm Deployment Deferred
Due to npm registry authentication and credential configuration, direct installation via the public npm registry is currently deferred. Please install directly from the GitHub repository using the options below.

Option 1: Pi Package Manager (Recommended)

From your project workspace, run:

Terminal 
pi install git:github.com/SaehwanPark/pi-safe-agent-team

Option 2: Clone to User Extensions Directory

Clone directly into your personal Pi extensions directory to make it available across all workspaces:

Terminal 
git clone https://github.com/SaehwanPark/pi-safe-agent-team ~/.pi/agent/extensions/pi-safe-agents-team

Option 3: Local Development Setup

Terminal 
git clone https://github.com/SaehwanPark/pi-safe-agent-team.git
cd pi-safe-agent-team
npm install
npm run check
pi -e ./index.ts

Quick Start & Usage

1. Spawning a Coordinated Worker

With the extension loaded in Pi, prompt your root model:

Prompt
Spawn a read-only scout agent to investigate the database schema in src/db.
Do not grant write permissions or shell execution. Ask for clarification if details are missing.

The root session invokes agent_spawn. The coordinator returns an actor identity, binds child-safe tools, and begins the child's session asynchronously without blocking you.

2. Monitoring via Slash Commands

Inspect the live coordination fabric using Pi slash commands:

  • /agents — Overview of active agents, health, and running turn counts.
  • /agents tree — Tree view of the parent-child hierarchy and roles.
  • /agents tasks — Deterministic task board with claims, dependencies, and results.
  • /agents resources — Real-time resource ownership, shared/mutable holds, and waiters.
  • /agents inbox — Inspection of unacknowledged and pending messages.

3. Standalone Coordinator TypeScript SDK

The state coordinator is pure TypeScript and can be tested without models or networking:

TypeScript
import { Coordinator } from "pi-safe-agents-team";

const coordinator = new Coordinator({ rootId: "demo" });

// 1. Register root
coordinator.dispatch("root", "agent.register", {
  rootId: "demo",
  role: "root",
  route: { provider: "local", model: "qwen", thinking: "medium" },
  capabilities: { maySpawn: true, mayWriteRepo: true },
});

// 2. Define a protected resource
coordinator.dispatch("root", "resource.define", {
  resourceId: "file:src/config.ts",
  kind: "file",
  path: "src/config.ts",
  permissions: ["write"],
});

// 3. Borrow exclusively & begin fenced write
coordinator.dispatch("root", "resource.borrow", {
  resourceId: "file:src/config.ts",
  mode: "mutable",
  leaseMs: 15_000,
});
const writeFence = coordinator.dispatch("root", "resource.begin_write", {
  path: "src/config.ts",
  fenceMs: 30_000,
}).value;

console.log("Write authorized, fence active:", writeFence.fenceId);

Operational Boundaries & Known Caveats

In the spirit of honest distributed-systems engineering, we document the system's exact operational boundaries:

Write Fences Across Broker Crashes
Write fences (resource.begin_write) are currently kept in coordinator memory. They strictly protect writes during normal broker operation (including lease lapses and root write interception). However, if the broker process crashes mid-write and restarts while the writer's filesystem call is still executing, the fence is not crash-durable. (A post-v0.1 recovery quarantine mechanism is planned to temporarily fence resources that had active leases upon restart).
Shell Isolation Scope
Shared-workspace shell (workspace: "shared") is strictly verified and read-only. Arguments are checked for path escapes and indirect file-reading flags (e.g. file -f, wc --files0-from). In contrast, worktree shell (workspace: "worktree") is an explicitly trusted developer escape hatch isolated by Git worktrees, not by coordinator resource locks.
