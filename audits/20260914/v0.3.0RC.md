# v0.3.0 RC audit

I audited current `main` at **`7db3778149561916fa893652e2913ca44ac27d18`**. The R10 work is substantially complete, and this is the first point in the audit series where I would characterize the project as genuinely **release-candidate quality** rather than still undergoing architectural hardening.

The current commit has all eight checks green, including Linux/macOS/Windows tests, LCM integration, R8 longevity, R9 broker chaos, and the new R10 production-default broker soak.  The R10 implementation also reports 204 tests passing, successful installed-tarball smoke, and good production-soak numbers: p95 task creation 6.50 ms, ACK 11.23 ms, rollback snapshot 0.97 ms, max rollback image ~542 KB, and p95 event-loop stall 2.27 ms.

My RC verdict is **almost GO**. I found one small residual correctness issue that I would fix before creating the `v0.3.0` tag. Everything else below is release-process/polish rather than a runtime blocker.

## RC-1 — one piece of the resource ABA fix is incomplete

The important R10 fix is correct: new resources receive a distinct `incarnation`, and snapshots now return:

```text
resourceId@incarnation@version
```

so an old resource and a later reuse of the same ID cannot have the same snapshot token.

The tagged-v0.2.3 migration is also correct, including the PR #43 follow-up that makes a legacy resource's synthesized incarnation stable across `active → retired` lifecycle events.

But the older `resource.inspect` stale-check API still does this:

```ts
requestedVersion !== resource.version
```

and does not check incarnation.

The public `agent_resource` tool likewise exposes `version` but no `incarnation` or snapshot token.

That means this schedule still exists:

```text
old parser:
  incarnation = A
  version = 1

parser retired
tombstone eventually pruned

new parser:
  incarnation = B
  version = 1

resource.inspect(parser, version=1)
→ stale = false
```

The documented safe handoff path correctly tells callers to compare `resource.snapshot`, so users following the new protocol are safe.  But the public stale predicate itself is now weaker than the generation semantics introduced specifically to eliminate ABA.

I would make `resource.inspect` accept an optional `incarnation`—or the opaque snapshot token—and define:

```text
stale =
    incarnation mismatch
    OR version mismatch
```

Keep version-only inspection for compatibility if desired, but describe it explicitly as intra-incarnation version checking. Add the exact prune → reuse → inspect-old-incarnation regression test.

This is a very small change. I recommend fixing it because doing so lets us say the R10 ABA issue is closed without qualification.

## Everything else from R10 looks properly closed

The **v0.2.3 → v0.3.0 state migration** is now real rather than hypothetical. The checked-in fixture was produced by tagged `v0.2.3` at `4cc71fa`, contains a v1 checkpoint plus committed journal tail, and covers an active root/child, task, request/message and mutable resource lease.

Current startup migrates v1 in memory, replays its tail, performs recovery, then replaces it with a v2 checkpoint before exposing the broker. Current state writes only version 2.   The public docs appropriately call this a one-way state upgrade and recommend backing up the state directory before its first v2 checkpoint.

The **ACK-proof architecture** is also a meaningful improvement. Proofs are no longer copied through every coordinator rollback/checkpoint. Instead, they go into an append-oriented `ack-proofs.jsonl` store with fsync, partial-tail repair and atomic periodic compaction; committed journal events remain authoritative if proof-store synchronization temporarily fails.

The **artifact admission bug** is fixed correctly: admission-aware trimming reserves one slot and preferentially removes resolved entries when the collection is exactly full.

And R10 now measures the actual production rollback path instead of deliberately avoiding it. The benchmark uses `BrokerServer` + `BrokerClient`, production 24-hour retention defaults, real journal writes, ACK proof storage, rollback snapshots, memory and event-loop monitoring.  The current 500-item CI benchmark itself completed in roughly nine seconds.

## RC-2 — put tarball smoke before the public GitHub Release

The tarball smoke itself is good. It:

* runs `npm pack`;
* verifies benchmark/scripts actually made it into the archive;
* installs the `.tgz` into a clean temporary package root;
* imports the published package surface;
* starts a broker and successfully performs a request.

And PR #42 says it has passed.

The only process issue is that ordinary CI doesn't run `smoke:package`; it lives in `.github/workflows/release.yml`.

That workflow is triggered by:

```yaml
release:
  types: [published]
```

So the sequence is technically:

```text
GitHub v0.3.0 Release becomes public
        ↓
release gates run
        ↓
npm publishes only if they pass
```

This safely protects **npm**, but it does not protect the GitHub Release itself.

For this release, the manual tarball verification plus current green main is enough that I would not make this another hard blocker. For future releases, add `smoke:package` as an ordinary CI/RC job, or have a tag/manual preflight run before publishing the GitHub Release.

## RC-3 — change the README's primary installation command

Since `v0.3.0` is intended to be the first polished public npm-facing release, I would change the primary recommendation.

Currently README's “Recommended” option is:

```bash
pi install git:github.com/SaehwanPark/pi-safe-agent-team
```

which follows the unpinned repository head. The npm option is shown as ordinary:

```bash
npm install pi-safe-agent-team
```

Current Pi documentation explicitly supports package-managed installs such as:

```bash
pi install npm:pi-safe-agents-team
pi install npm:pi-safe-agents-team@0.3.0
pi install git:github.com/SaehwanPark/pi-safe-agent-team@v0.3.0
```

and distinguishes pinned git refs from moving repository heads. ([GitHub][1])

For the release README I'd make:

```text
Recommended:
pi install npm:pi-safe-agents-team

Pinned:
pi install npm:pi-safe-agents-team@0.3.0

GitHub:
pi install git:github.com/SaehwanPark/pi-safe-agent-team@v0.3.0
```

and move the unpinned `main` install into a “development/latest” subsection.

That makes the public release behavior much more predictable.

## Two non-blocking things I'd retain as post-0.3 work

The new ACK proof store is “cold” in the important sense that proofs are outside coordinator rollback/checkpoint state, but `AckProofStore.open()` still loads **every historical proof** into `proofsByKey` plus a per-message index. Compaction removes duplicate disk records, not old logical proofs.

I wouldn't delay 0.3.0 for this. State directories are session-scoped and this is vastly better than copying the proofs on every transaction. But if extremely long-lived fabrics become common, the next scale step is an actual disk-indexed proof database/sharded index rather than an indefinitely growing heap map.

Separately, the current Pi packaging documentation recommends treating Pi core packages—including `typebox`—as peer dependencies with `*`. ([GitHub][1]) The current package has bounded Pi peer ranges and puts `typebox` in ordinary dependencies.  That is not causing current tests or tarball smoke to fail, so I would regard alignment with that convention as cleanup rather than an RC blocker.

One reproducibility improvement is also worth making eventually: the release workflow pins Pi to `0.85.1`, which is good, but checks out `pi-local-context-manager` without a `ref`, so the release gate depends on whatever LCM's default branch contains on release day.  Pinning a known compatible LCM release/commit would make the release gate reproducible.

# RC verdict

**Runtime:** essentially ready.

**R10 closure:** good. The state migration, production soak, ACK durability, artifact capacity and generation identity changes are materially implemented rather than papered over.

**Public packaging:** good enough, with the tarball smoke already demonstrated. Package and lockfile both consistently say `0.3.0`, and the changelog has been reorganized around user-facing release themes rather than audit-round jargon.

**Tag status:** `v0.3.0` does not exist yet, which is exactly what we want during the RC audit. The latest public tag remains `v0.2.3`.

My recommendation is therefore:

1. **Fix RC-1 (`resource.inspect` incarnation-aware stale checking).**
2. Run the normal CI plus `npm run smoke:package` once on that final commit.
3. Preferably adjust the README installation commands before the tag; pinning LCM in the release workflow is also worthwhile but not mandatory.
4. Tag **that exact commit** as `v0.3.0`, create the public GitHub Release, and let the release workflow perform its three-OS chaos gates, production soak, LCM smoke, tarball verification and npm trusted publication.

After RC-1, I would give **v0.3.0 a GO**. I would not do an R11 before release unless the RC fix itself touches broader coordination logic.
